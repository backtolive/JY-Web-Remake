# opcode 55：客體記憶體與候選處理段限定追查

2026-11-14。Phase 1／2；Status: **執行入口未確認，完整語意未驗收**。沿用唯一的 DOSBox-X PID 7508、遊戲 HWND `0x38085A` 與隔離第三槽。原始 `KDEF.GRP` 保持 SHA-256 `135c5e097a7fe561ee931046e1bebf55de9b469678e3d111d8e9f2c6bb600e06`；事件 464 原段位於 byte 71352，長 210 bytes，SHA-256 `0a23ad50eb196bf088274a3187b6cca485bf08646fdda1e658439c688f69eff4`。第三槽的合成場景與位置只供取樣，並非原版自然進度。

## 可重現的唯讀觀察

- 以內建 debugger 的 `BREAK`、`MEMDUMPBIN 0168:00000000 02000000`、`RUN`，分別於標題、進入場景 32 與原始事件 464 執行後取得 32 MiB 客體記憶體快照。`BPLIST` 起始為空；這三次快照沒有設定斷點。檔案留在 ignored `assets/generated/dosbox-x/session-002/MEMOP55*.BIN`。
- 原始事件 464 的 210 bytes 在**事件執行後**的快照中完整出現在客體 offset `0x0028EE90`；在標題與進場前快照均未找到。另一處完整匹配位於 `0x0000ADF0`。這只證明事件資料於互動後在記憶體中，不能證明某個候選處理段已執行。
- 在事件後快照，`0x001E1554` 附近有 `2E FF 24 95 09 12 1E 00`，即以數值索引查 `0x001E1209` 的 32-bit 跳轉表；索引 55 的表項位於 `0x001E12E5`，值為 `0x001E1ADF`。該段含 `E8 E3 35 00 00`，靜態相對呼叫目標為 `0x001E50D9`。候選函式內可見 22-byte 間距、讀取 `0x0027A694` 基址及比較／返回兩個值的指令序列。這是**本機二進位候選路徑**，尚未以停在該地址的執行紀錄確認。

## 限定執行檢查

同一 PID 內回標題，重新讀入隔離第三槽。第一次按 `Up` 後唯讀記憶體未找到事件 464，於是只擷取一次精確遊戲視窗；畫面顯示角色仍在世界地圖入口。依已記錄的入場流程再按一次 `Up`，場景 32 槽 0 唯一匹配事件 464，前值 `[1,0,464,-1,-1,7448,7490,7448,20,31,25]`。設定唯一 `BP 0160:001E1ADF` 後，再按 `Up` 觸發事件；槽 0 的原前值消失，CPU 之後回到 `0160:001D542C`，但沒有觀察到停在 `0160:001E1ADF`。因此這次**不能證明該候選表項就是實際執行入口**，也不能從靜態位元組裁定 `-1` 的分支。`BPDEL *` 後 `BPLIST` 為空。

先在同一 PID 內將客體回標題，再依 manifest 還原隔離第三槽六檔。R3、D3 雜湊分別回到 `aa2f4dee1b6b73120ebe92a100535e30c7d608cb0d2b0dd38ffa900d9f47c22c`、`8ec61fa55fcdf698223534753b19e453f7d14f9510c3361ef4641e53ffec9d56`；其餘四檔也與 manifest 的 `before` 一致。DOSBox-X PID 7508 未關閉。

追加一次 debugger 模式準備時，隔離第三槽再次由基線建立；載入時序未得到「已進場且事件未觸發」的唯一匹配，故**沒有設定新的斷點**。重新回標題後，精確視窗標題檢查拒絕了 `Up`：視窗標題已由 `Z` 變成 `COMMAND`。單一精確遊戲視窗擷取顯示客體停在 `C:\>`，表示遊戲程序已退出到 DOS shell；沒有繼續送按鍵或臆測畫面。此時再依第二份 manifest 還原六檔，`BPLIST` 仍空；DOSBox-X 本身維持同一 PID 7508。之後在此已確認的提示符輸入 config 所列的 `z.com`，遊戲同一 PID 回到可見標題選單。

第三次隔離第三槽載入時，在場景 32 槽 0 唯一確認 `[1,0,464,-1,-1,7448,7490,7448,20,31,25]` 後，依次執行 `BREAK`、`BP 0160:001E1ADF`、`RUN`，才按 `Up`。事件仍執行完畢，沒有停在候選入口。緊接著設 `BP 0160:001D543C` 作控制組，`BREAK`／`RUN` 後 `EV CS EIP` **確實停在 `0160:001D543C`**。因此這個 debugger 的單點斷點可以生效；候選 `0x001E1ADF` 沒有命中，不能只歸咎於正常執行模式。控制斷點隨即清除並 `RUN`，`BPLIST` 為空；客體回標題後第三份 manifest 的六檔全部還原，DOSBox-X PID 7508 與遊戲視窗維持開啟。此結果仍不能證明 opcode 55 真正的入口或分支。

最後用先前已測過道具輸出的最短 Synthetic Script `55,2,-1,3,0,2,57,1,7`，只測候選入口是否命中。以新 manifest 暫換隔離 `KDEF.GRP` 的事件 1017；第三槽指向該事件。場景 32 槽 0 在觸發前唯一匹配事件 1017；`BREAK`、`BP 0160:001E1ADF`、`RUN` 後觸發，事件槽原前值消失，但 `EV CS EIP` 先後為 `0160:001DE2BD`、`0160:001DE2BB`，仍未停在候選地址。這是**入口對照**，未重測道具結果。斷點清除、客體回標題、第三槽六檔與 `KDEF.GRP` 均依各自 manifest 還原；KDEF 回到上述原始 SHA-256。同一 PID 7508 維持開啟。

本輪靜態候選段與[先前合成腳本的道具結果](opcode-55-dos-branch-probe-20261114.md)尚不能接成同一條已驗證控制流。**後續前置核對修正**：最短合成事件的「前值整筆紀錄消失」至少有一部分是走動時圖號改變造成的搜尋失配；本輪[觸發守門追查](opcode-55-trigger-preflight-20261114.md)未在背包或客體記憶體中確認該合成腳本執行。因此其候選斷點未命中，**不能排除** `0x001E1ADF` 是真正 handler。主迴圈控制斷點可命中只證明 debugger 能停機。先前「選到相等／不相等跳轉」仍是**對輸出結果的解釋假說**；道具增加與否是原紀錄的實測輸出。下一步先建立可重現的正向觸發證據，再記錄 opcode 55 命中時的 CS:EIP／游標／參數。
