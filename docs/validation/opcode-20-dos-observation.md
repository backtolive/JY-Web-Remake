# 原版 DOS 事件 581 的滿隊分支

2026-11-12。Phase 1／2，局部原版執行證據。原始事件 581 位於 KDEF byte 88988；事件資源 SHA-256 `ac27f3fee143440e3d3af716d1b460e703959545f58d7f93a604c3a7f5e74386`。候選切分在首段對話後為 `20(0,6)`，接 `1(175,49,0)`、`0`、`7`；另一支接 `14`、`3` 等指令。KDEF 未修改。此案例只檢驗原版 DOS 在兩種隊伍狀態的實際分支，不把社群文件「隊伍全體內力降為 0」當作原版結論。

隔離 `session-002` 第三槽將場景 32 槽 0 指向原始事件 581，合成解鎖入場；兩案分別設定隊伍 `[0,-1,-1,-1,-1,-1]` 與 `[0,1,2,3,4,5]`。一人案首段對話為「賢弟，我們走了吧。」（`z_427.raw1.png`）；關閉後，執行中場景 32 槽 2 從 `[1,2,-1,-1,-1,2718,2718,2718,0,30,21]` 變為 `[0,0,-1,-1,-1,-1,-1,-1,0,30,21]`。這項事件槽修改屬分支後續的 opcode 3 效果，不能直接算作 opcode 20 寫入。

六人案在執行中記憶體讀回隊伍 `[0,1,2,3,4,5]`，確認事件槽 0 為 581。首段對話後出現「你的隊伍已滿，無法再加入」（`z_435.raw1.png`）；關閉後場景 32 槽 2 仍為原值，隊伍也維持六人。這支持本案例的 opcode 20 為「隊伍是否已滿」的條件分支。滿隊提示由後續 opcode 1 顯示，事件槽變化由另一支的後續指令造成。

變更的來源值、byte offset、SHA-256 與六檔備份見 ignored 的 `synthetic-op20-event581-party1-20261112/manifest.json` 及 `synthetic-op20-event581-party6-20261112/manifest.json`。兩案均在關閉唯一精確 DOSBox-X 程序後還原第三槽，六檔 SHA-256 回到基線。首段入場標牌尚未退場時的一次按鍵未觸發事件，已由遊戲畫格及未變更的執行中事件槽辨識，不列為 opcode 負面證據。

尚未驗證 `0,6` 兩個參數的逐一意義、其他容量或隊伍排列、完整相對跳轉公式、自然遊戲流程可達性。此案例不證明 opcode 20 的所有參數變體。
